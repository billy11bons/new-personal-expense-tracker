## Зависимости

UI вызывает `initializeLedger` с репозиторием из `createBrowserRepository`. Инициализатор зависит от абстракции `LedgerRepository`; он не обращается к browser API. Локальный адаптер получает объект с `getItem`/`setItem` через конструктор. Это позволяет проверять ошибки хранения и сохранение без React и без браузера.

`domain/` содержит только TypeScript-функции и типы. Адаптер использует общую runtime-валидацию домена при чтении и записи. Расчёты получают Ledger и Period; не знают, откуда пришли данные. Ограничения импортов и browser globals закреплены ESLint для доменного слоя.

Будущий Supabase должен реализовать `load()` и `save(ledger, expectedRevision)`, включая атомарную проверку revision, изоляцию владельца и преобразование таблиц в Ledger. Заменяется фабрика адаптера; расчёты и валидаторы не меняются. Серверный API/RPC и Auth относятся к будущей интеграции и сейчас отсутствуют. Контракт сохраняет целый снимок — это осознанное упрощение небольшого локального MVP.

## Модель

- User: id, currency (`USD` на этом этапе).
- Income: id, userId, date, amountMinor, note.
- Expense: те же поля и categoryId.
- Category: id, userId, name, archived.
- Budget: id, userId, month, amountMinor; уникальный месяц в рамках пользователя.

Все записи имеют существующего владельца; расход ссылается на существующую категорию. Архивная категория допускается в истории, но `validateNewExpense` запрещает новые расходы в неё. Stage 3 реализует изменение категорий и операций через чистые доменные команды. При редактировании исторического расхода разрешено сохранить его прежнюю архивную категорию; новые назначения архивных категорий запрещены.

## Хранение

Один ключ `case02.personal-expense-tracker`, envelope `schemaVersion: 1`, положительная целочисленная revision и Ledger. Отсутствие ключа означает возможность seed; пустой или повреждённый JSON не считается отсутствием. Неизвестная версия отклоняется без автоматической миграции. Успешный save увеличивает revision, а возвращаемый объект независим от сохранённой записи.

Чтение существующей записи и проверка revision происходят до записи, без `await` между ними. Это защищает последовательные обращения в одной вкладке. Между вкладками атомарность не гарантирована: до будущего решения синхронизации предполагается одна активная вкладка. Ошибки чтения/квоты не маскируются успешным статусом. Инициализация конкурентных вызовов обрабатывает конфликт через повторное чтение (в том числе React Strict Mode).

На сервере localStorage не используется: доступ возникает только в клиентском effect. Серверная и первая клиентская отрисовка имеют одинаковый текст загрузки.

## Расчёты

Суммы операций — положительные безопасные целые числа центов; бюджет может быть нулевым. Парсер десятичных строк использует BigInt для перевода в центы; сумма проверяется на переполнение Number.MAX_SAFE_INTEGER. Агрегаты не хранятся отдельно.

Календарные даты YYYY-MM-DD, годы 0001–9999; несуществующие дни отклоняются. Неделя понедельник–воскресенье. UTC используется только для календарного сдвига, без пересчёта введённой даты в другой часовой пояс. Период, выходящий за поддерживаемый диапазон лет, отклоняется. Общий месячный бюджет вычитает все расходы месяца. Отсутствие бюджета возвращает null.

Фильтрация дат внутри расчётов реализована; пользовательские фильтры и группировка/графики относятся к Stage 4.

## Команды и UI Stage 3

`domain/commands.ts` содержит `saveTransaction`, `deleteTransaction`, `saveCategory`, `setCategoryArchived`, `saveBudget`. Все функции принимают Ledger и возвращают новый валидный Ledger, не меняя исходные записи. Валидация выполняется до записи. `FormValidationError.fields` связывает понятные сообщения с полями формы. Денежный ввод и вывод используют точное преобразование строки и целых центов; код компонентов не рассчитывает финансовые итоги.

Тип операции проверяется в домене. При смене типа старый элемент удаляется из соответствующего массива и ровно один элемент с тем же ID добавляется в другой. Ссылка на операцию состоит из типа и ID, поэтому допустимые в схеме одинаковые ID в разных массивах не приводят к удалению неверной записи. Доход не получает categoryId. Идентификаторы новых операций/категорий/бюджетов выдаёт браузерный crypto.randomUUID при открытии формы; повтор после отказа записи использует тот же ID.

`domain/transactions.ts` строит единый список, сохраняя тип каждой операции, и сортирует по убыванию календарной даты. Доходы/расходы различаются подписью, знаком и цветом. Фильтрация и отчёты здесь не добавлялись.

`LedgerProvider` размещён в root layout, хранит текущие Ledger/revision и разделяет их между маршрутами. Общая функция `commit(change)` сначала применяет доменную команду, затем вызывает существующий `repository.save(next, revision)`; только успешный результат становится видимым состоянием. Ref-блокировка защищает от повторного быстрого сохранения. Ошибка не скрывает форму и не меняет сохранённый снимок. Повторная загрузка явно перечитывает данные; незаписанный ввод сбрасывается.

Контракт `LedgerRepository`, схема v1, локальный адаптер, демоданные и зависимости Stage 2 не изменены. Общая инициализация заменяет отдельный компонент `storage-status.tsx`, который удалён как дублирующий.

Удаление использует стандартный HTML dialog: фокус ограничен диалогом, начальный фокус на отмене, Escape отменяет. Ошибка удаления показывается внутри диалога; запись остаётся до успешного сохранения.

Повторно прочитаны локальные руководства Next.js 16.3.4: layouts-and-pages, server-and-client-components и Link. Используются серверные страницы с клиентскими экранами, общий layout и next/link; Supabase/Auth, Server Actions и сетевые API не добавлялись.
